## Можно ли собрать NFS-сервер на Rust из готовых ONC RPC/XDR-крейтов (это и есть конкуренция RPC-слою nfs-mamont)

### Takeaway
Технически да. Единственный «конструктор», в котором есть всё, что нужно серверу (TCP/UDP-сервер с dispatch, rpcbind v4, RPC-over-TLS по RFC 9289, генерация кода из `.x`), это стек `onc-rpc-*` (jcalcote/oncrpc-rs). Ему 5 месяцев, у него 0 звёзд, один автор и нет внешних пользователей. Остальные крейты закрывают только часть задачи: `onc-rpc` даёт лишь конверт RPC-сообщения, `fastxdr` только декодирует, `xdr-codec`/`xdrgen` заброшены с 2017 года, а `serde-xdr` под GPL-3.0. Поэтому все реальные NFS-проекты на Rust либо пишут свой RPC/XDR-слой, либо форкают существующий: так поступили AWS efs-proxy, nfs-rs, nfs3/nfsserve и сам nfs-mamont.

### Inferences
- Если строить NFSv3-сервер на `onc-rpc-*`, стек закроет транспорт, record marking, dispatch, rpcbind и TLS, но не NFS-семантику: обработку 22 процедур RFC 1813, MOUNT, file handles, VFS, NLM/NSM. Поэтому стек конкурирует только с RPC/XDR-слоем nfs-mamont, а не с сервером целиком.
- Сейчас «соберу сервер из крейтов» реалистично только на `onc-rpc-*` + `onc-rpc-gen` по RFC 1813 `.x` или на `nfs3_types`. Первый вариант новый и рискованный (см. раздел о стеке `onc-rpc-*`). Второй фактически означает использовать кодовую базу конкурента (Vaiz/nfs3).
- Download-метрики RPC/XDR-крейтов говорят о клиентах AWS EFS, а не о популярности как фундамента для серверов (см. следующий раздел).

### Gaps
- Не найдено ни одного публичного NFS-сервера, построенного на `onc-rpc-*` (0 внешних обратных зависимостей на crates.io). Независимых интероп- и нагрузочных данных по этому стеку нет.
- Не проверено, собирает ли серверная часть `onc-rpc-server` многофрагментные записи (клиентский runtime собирает, см. ниже).

## onc-rpc (domodwyer): откуда ~7,8 млн загрузок, возможности, сопровождение и качество

### Takeaway
Почти все 7,8 млн загрузок дают сборки AWS efs-utils (компонент efs-proxy на Rust) и их многочисленные форки, а также scanopy. Эти проекты не опубликованы на crates.io, поэтому у крейта 0 обратных зависимостей. Сам `onc-rpc` — качественный, но узкий кодек конверта ONC RPC: zero-copy десериализация, только безопасный Rust, фаззер и proptest. Транспорта, сервера и поддержки фрагментированных записей нет. Крейт в режиме поддержки, и с 2025 года его активность в основном составляют обновления от dependabot.

## Модульный стек onc-rpc-* (jcalcote/oncrpc-rs): кто стоит, связь с onc-rpc, полнота, зрелость, шанс стать стандартом

### Takeaway
Восемь крейтов `onc-rpc-*` в одиночку пишет John Calcote (github.com/jcalcote/oncrpc-rs, первый коммит 2026-05-23). С домодвайеровским `onc-rpc` их связывает только похожее имя: другой автор, другая лицензия, собственные wire-типы, никакой зависимости. По набору функций это самый полный ONC RPC-стек на Rust на 2026-10-30: TCP/UDP-клиент и сервер, sync и async dispatch, rpcbind v4, STARTTLS по RFC 9289 и прямой TLS, кодогенерация из `.x`. Но зрелость ранняя: 0 звёзд, 42 коммита, 0.x с ломающими релизами, нет внешних пользователей, в планах прямо записано «hardening» под интероп и нагрузку. Стандартной основой Rust NFS-серверов он может стать только при появлении пользователей. Пока это кандидат на наблюдение, а не на внедрение.

### Inferences
- По чек-листу «сервер + TCP/UDP + rpcbind v4 + RFC 9289 + кодоген из `.x`» других кандидатов на Rust среди проверенных крейтов нет. Упоминание oncrpc4j подсказывает ориентир: Java-стек dCache, на котором работает NFS-сервер dCache.
- Для горячего пути NFS модель стека хуже подходит, чем у nfs-mamont. Обработчик получает целиком материализованный `payload: Bytes` (запись читается в растущий `BytesMut`), а декодер opaque копирует данные через `copy_to_bytes`. На большом WRITE (скажем, 1 MiB) получится полная буферизация записи плюс копия, а не потоковая запись в заранее выделенный пул с backpressure. Это вывод по коду, бенчмарков нет.
- Риски: bus factor 1, ломающие 0.x-релизы раз в несколько месяцев, нет внешних пользователей и интероп-отчётов. Из аутентификации только `AUTH_NONE` и `AUTH_SYS`, RPCSEC_GSS нет.
- Шанс стать стандартом есть, если появятся пользователи. Особенно для NFSv4, где ручной XDR дорог, а `.x` из RFC можно скормить генератору. На 2026-10-30 стек стоит наблюдать и, возможно, точечно использовать (`onc-rpc-tls` как эталон RFC 9289, `onc-rpc-bind` для rpcbind v4), но не строить на нём ядро.
- Платформенная поддержка: всё на tokio и rustls, OS-специфичного кода не видно. Вероятно, Linux, macOS и Windows, но CI-матрица ОС не опубликована.

### Gaps
- Не проверено, как сервер обрабатывает многофрагментные записи и лимиты на них. Опубликованных бенчмарков и интероп-тестов с Linux knfsd, клиентами или rpcbind нет.
- Личность и мотивация автора (связь с dCache или коммерческим NFS-продуктом) не установлены.
- Отображение `oncrpcgen` в Rust не проверялось на полном RFC 1813 `.x` и на NFSv4 (RFC 7531 и 7863); в тестах только `nfs3_io.x`.

## Legacy- и прочие XDR-крейты: xdr-codec/xdrgen, serde-xdr, xdr-rs-serialize, fastxdr, facet-xdr

Ни один из этих крейтов не годится как основа нового NFS-сервера на 2026-10-30. `xdr-codec`/`xdrgen` заброшены с 2017 года, их миллионы загрузок дали пины efs-utils 2.x, и AWS теперь держит собственный форк. `serde-xdr` под GPL-3.0, тянет устаревший `failure`, а его свежий всплеск загрузок аномален. `xdr-rs-serialize` вырос из блокчейн-проекта и тоже заброшен. `fastxdr` хорошо декодирует zero-copy, но генерирует только декодер, на crates.io застрял в 2020 году и, как задокументировано, паникует на обрезанном padding. `facet-xdr` — универсальная reflection-сериализация в стадии rc, без RPC и с MSRV 1.92.

## Сравнение с рукописным RPC/XDR-слоем nfs-mamont: преимущество или бремя сопровождения

### Takeaway
У nfs-mamont более «системный» дизайн, чем у любого из рассмотренных стеков. Head-window буферизуется синхронно, данные WRITE потоково пишутся прямо в пул фиксированных буферов с backpressure, ответ READ уходит через `write_vectored`, ошибки разделены на структурные и семантические с гарантированным сбросом остатка фрейма, wire-дискриминанты типизированы. Это реальное отличие на горячем пути. Цена — собственные парсеры и сериализаторы на каждую процедуру (около 8,6 тыс. строк в `rpc/`, `parser/`, `serializer/`, `allocator/` вместе с тестами). Не хватает фаззинга (workflow есть, целей нет), фрагментированных записей, UDP, AUTH_TLS и RPCSEC_GSS. Для NFSv4 ручной подход станет дорогим.

### Cited Findings
- `FrameReader` буферизует «head window» каждого RMS-фрейма размером `min(frame_size, capacity)`. Аргументы разбираются синхронно через `std::io::Read`, и чтение не выходит за границу фрейма. WRITE-данные читаются через `read_body_exact()` сначала из буфера, потом напрямую из сокета. Есть `discard_body()` и `discard_rest_of_frame()`. — `/home/user/nfs-mamont/nfs-mamont/src/parser/read_buffer.rs`
- Размер head window по умолчанию — `DEFAULT_SIZE = 2500` байт. Аргументы любой процедуры, кроме opaque-данных WRITE, обязаны в него поместиться. — `/home/user/nfs-mamont/nfs-mamont/src/parser/parser_struct.rs`
- `adapter_for_write`: проверяет, что заявленная длина вместе с padding не превышает `frame_remaining`; берёт буфер через `Allocator::allocate()`, который ждёт освобождения пула; заполняет его кусками через `read_body_exact`; затем отбрасывает padding. `adapter_for_read` выделяет выходной буфер READ из того же аллокатора ещё на этапе разбора. — `/home/user/nfs-mamont/nfs-mamont/src/parser/parser_struct.rs`
- Ответ READ собирается в `IoSlice` из заголовка, кусков буфера и padding и отправляется через `write_vectored` («writev-style syscall»). Остальные ответы проходят через промежуточный буфер на 4096 байт и `write_all`. — `/home/user/nfs-mamont/nfs-mamont/src/serializer/server/serialize_struct.rs`
- Аллокатор: заранее выделенный пул буферов фиксированного размера (`ArrayQueue` и `tokio::sync::Semaphore`), опциональная фича `mlock`, публичные трейты `Allocator`/`Buffer`. Внутри `unsafe` с сырыми указателями (`UnownedBuffer::from_raw_parts`). — `/home/user/nfs-mamont/nfs-mamont/src/allocator/mod.rs`; `/home/user/nfs-mamont/nfs-mamont/src/allocator/buffer.rs`
- Ошибки: структурный `parser::Error` (InvalidData, FormatMismatch, MaxElemLimit, EnumDiscMismatch и т.д.) отделён от семантического `rpc::Error` (RpcVersionMismatch, `Auth(AuthStat)`, ProgramMismatch, ProcedureMismatch, ProgramVersionMismatch). Ошибка оборачивается в `ErrorWrapper { xid }`. `msg_type` и `rpcvers` проверяются сразу; запись с `MessageTypeMismatch` read task отбрасывает. Версия программы проверяется раньше процедуры (RFC 5531 §8.1). `finalize_parsing()` требует, чтобы после разбора не осталось хвоста. При любой ошибке остаток фрейма сбрасывается. — `/home/user/nfs-mamont/nfs-mamont/src/parser/error.rs`; `/home/user/nfs-mamont/nfs-mamont/src/rpc/mod.rs`; `/home/user/nfs-mamont/nfs-mamont/src/parser/parser_struct.rs`
- Типизированные wire-enum: `#[repr(u32)]` и `num_derive::{FromPrimitive, ToPrimitive}` для `NfsProc`, `AuthFlavor` и других. ### Inferences
- **Отличие:** потоковый WRITE в ограниченный пул с backpressure, `writev` для READ и строгий discard фрейма нигде больше в готовом виде не встречаются. `onc-rpc` сериализует в непрерывный буфер. `onc-rpc-server` материализует запись целиком и копирует opaque. Этот дизайн можно подавать как техническое преимущество, но лучше подкрепить бенчмарком против `onc-rpc-server` и nfsserve.
- **Терминология:** «zero-copy» у nfs-mamont значит «без промежуточной копии в user space» (сокет пишет прямо в буфер пула), а у `onc-rpc`/`fastxdr` — «заимствование из входного буфера при декодировании». Это разные свойства, и в сравнительных материалах их стоит различать.
- **Бремя:** ручные per-procedure-модули на 22 процедуры NFSv3, MOUNT и NLM поддерживать терпимо. NFSv4.x (COMPOUND и десятки операций, атрибуты-битмапы) вручную резко увеличит объём и риск ошибок. Здесь генерация из `.x` (RFC 7531, RFC 7863) почти наверняка дешевле.
- **Главный разрыв качества против `onc-rpc`** — отсутствие фаззинга при уже готовом workflow. Опыт `onc-rpc` (ошибки разбора opaque найдены и исправлены в 2025) и патч fastxdr в nfs-rs показывают, что именно здесь прячутся паники и переполнения.
- **Совместимость:** без `AUTH_TLS` клиент, который зондирует RPC-with-TLS (RFC 9289), получит от nfs-mamont ответ, рождённый структурной ошибкой, а не явный `AUTH_ERROR`. Нужно проверить, что клиенты корректно откатываются на обычный режим.

### Gaps
- Нет измерений производительности nfs-mamont против `onc-rpc-server` и fastxdr-декодирования.
- Не проверено, какой RPC-ответ nfs-mamont отправляет на `EnumDiscMismatch` в заголовке (неизвестный flavor) и как на это реагирует клиент Linux с `xprtsec=tls`.

## Ландшафт NFS-клиентов на Rust и пригодность для интеграционных тестов nfs-mamont без монтирования ядром

### Takeaway
Для NFSv3-сервера практически годятся три чисто Rust-клиента. `nfs3_client` (Vaiz) лучше всех подходит для протокольных тестов: низкоуровневые вызовы любой процедуры NFSv3, MOUNT, portmapper, свои credentials, tokio или smol, MSRV 1.88. `nfs-rs` (crates.io; код NetAppLabs, развиваемый инженерами Lenovo NetApp) подходит для сценарных end-to-end-тестов: высокоуровневые файловые операции, порты задаются в URL, есть Python-биндинги, но MSRV 1.95 и 54 тыс. строк. `nfs` (lvillis) совсем свежий и рискованный. `libnfs`/`libnfs-sys` — устаревшие биндинги к C-библиотеке. ## Возможности для nfs-mamont: переходить на общий RPC-стек, контрибьютить в него или сохранить собственный

### Takeaway
Рекомендуемая стратегия — сохранить собственный RPC/XDR-слой для NFSv3: это реальное отличие на горячем пути, а альтернативы либо уже по охвату (`onc-rpc`), либо незрелы и ориентированы на копирование (`onc-rpc-*`). При этом стоит заимствовать практики и точечные компоненты. Самое дешёвое: настоящие цели cargo-fuzz для уже существующего workflow. Дальше: сборка фрагментов (issue #124), rpcbind v4 и RFC 9289 по образцу `onc-rpc-bind` и `onc-rpc-tls`, интеграционные тесты на `nfs3_client` и `nfs-rs`. Для NFSv4 серьёзно рассмотреть генерацию XDR-типов из `.x` (`onc-rpc-gen` или свой build.rs), оставив ручными framing и путь READ/WRITE.

### Cited Findings
- Чего нет в nfs-mamont и что есть в стеке jcalcote:
  - многофрагментные записи: в nfs-mamont не поддержаны (TODO #124), в `onc-rpc-runtime` поддержаны с лимитами;
  - UDP: в nfs-mamont нет, у jcalcote есть;
  - rpcbind: nfs-mamont умеет только PMAP v2 SET/UNSET, у jcalcote rpcbind v4;

### Inferences
- **Не переходить** на `onc-rpc` (domodwyer): он дублирует уже написанное (конверт), не умеет фрагменты и не даёт транспорта. Выгода близка к нулю.
- **Не строить ядро** на `onc-rpc-server`. Bus factor 1, нет пользователей, модель «запись целиком в `Bytes` плюс копия opaque» противоречит главному техническому тезису nfs-mamont. Вместо этого полезно:
  - использовать его как эталон при реализации сборки фрагментов (лимиты 128 MiB и 1024 фрагмента — разумная точка отсчёта), rpcbind v4 и STARTTLS по RFC 9289;
  - при желании контрибьютить в него NFSv3-интероп-тесты или API для «streaming/borrowed opaque». Если стек выстрелит, nfs-mamont окажется в числе его ранних и заметных соавторов.
- **Быстрые победы с высокой отдачей:**
  1. Цели cargo-fuzz для `RpcParser::next_message` над произвольным байтовым потоком, плюс proptest для примитивов.
  2. Отдельный член workspace с интеграционными тестами на `nfs3_client` (протокол) и `nfs-rs` (сценарии), запускаемый только на свежем тулчейне.
  3. Явная обработка неизвестного flavor (`AUTH_TLS`) как `AUTH_ERROR`/`AUTH_BADCRED` вместо структурной ошибки.
- **Для NFSv4 (roadmap):** ручной XDR для COMPOUND и атрибутов станет главным источником бремени сопровождения. Разумный гибрид: генерировать типы и codec NFSv4 из `.x` (RFC 7531 и 7863) через `onc-rpc-gen` или собственный build.rs-генератор, а ручными оставить `FrameReader`, аллокатор, путь READ/WRITE и обработку ошибок. Так делает и AWS (сгенерированные биндинги поверх своего транспорта).
- **Позиционирование:** в сравнительных материалах формулировать отличие точно. Не «у нас zero-copy XDR» (так заявляют и `onc-rpc`, и `fastxdr`), а «потоковый WRITE в ограниченный пул с backpressure, `writev`-ответы READ и строгий discard фрейма». И подтвердить это бенчмарком.
