## 1. Происхождение: форк или переписывание nfsserve, авторы и мейнтейнеры, мотивация, лицензия

### Takeaway
nfs3 — это «жёсткий» форк xetdata/nfsserve (история upstream импортирована в репозиторий, но GitHub-связи fork нет) с глубоким рефакторингом. XDR-слой, trait API, абстракция file handle, workspace и клиент написаны заново, а ядро обработки RPC/NFS и часть README унаследованы. Единственный мейнтейнер — Vaiz (Evgenii). nfs3_server распространяется под BSD-3-Clause (унаследовано от nfsserve), остальные крейты под Unlicense (public domain).

### Inferences
- Классификация: форк с переписыванием, а не переписывание с нуля. Унаследованы схема обработки RPC-сообщений (`rpcwire.rs`, `nfs_handlers.rs`), семантика memfs/mirrorfs, transaction tracker (детектор ретрансмиссий от Roland Rauch, 2024-08) и большая часть README. Заново сделаны XDR-кодек (`nfs3_types` + `nfs3_macros`), разделение на RO/RW-трейты, generic `FileHandle`, клиент, тестовый крейт и CLI.
- Вероятная мотивация форка — застой upstream в 2024 – начале 2025 года: релизов с 2024-04 по 2026-04 не было, последний merge — 2024-09, сейчас там 11 открытых PR. К этому добавлялось желание делать глубокие breaking-изменения (workspace, Rust 2024, свой XDR, поддержка Windows). Явного заявления автора о причинах я не нашёл.
- С 2026-04 upstream nfsserve снова жив под крылом Hugging Face (0.11.0) и на порядки популярнее: около 1,4 млн загрузок против около 44 тыс. у nfs3_server. Аргумент «единственный поддерживаемый наследник nfsserve» nfs3 больше не работает, и у одного кода теперь две расходящиеся линии.
- Комбинация лицензий: для nfs3_server (BSD-3) нужно сохранять copyright-уведомление; types, client и macros фактически public domain. Обе лицензии разрешительные, сопоставимы с MIT у nfs-mamont.

## 4. Функциональность и архитектура: trait API сервера, процедуры, MOUNT/portmap, auth, транспорт, file handles, платформы; nfs3_types/nfs3_macros

### Takeaway
nfs3_server — асинхронный сервер на tokio (только TCP) с двумя трейтами: `NfsReadFileSystem` (RO) и `NfsFileSystem` (RW, надстройка над RO). Методы — нативные `impl Future + Send` (RPITIT), адресация через generic opaque-хэндл (до 56 байт) и `(dir handle, name)`. Сервер обслуживает 20 из 22 процедур NFSv3: MKNOD и LINK отвечают `PROC_UNAVAIL`. MOUNT есть без DUMP, portmapper поддельный (только GETPORT на том же порту). Из аутентификации — только AUTH_UNIX с глобальным хуком `authorize`, ACCESS не проверяет права. DRC отбрасывает ретрансмиссии вместо повтора ответа. В nfs3_types свой XDR-кодек с derive-макросом и типами `Cow`, но декодирование всегда копирует, так что zero-copy есть только на стороне кодирования.

### Inferences
- API проще, чем у nfs-mamont: 2 трейта и около 20 методов, многое реализовано по умолчанию (`readdir` через `readdirplus`, `lookup_by_path`, `fsinfo`), есть RO-адаптер. Модель адресации по id/handle, path-based API нет. Реализация обязана поддерживать отображение handle → объект, в mirrorfs для этого используется интернирование путей (`intaglio`, `symbols_cache`).
- Zero-copy в nfs3 частичный. При кодировании можно заимствовать срезы (`Cow::Borrowed`), но READ всё равно аллоцирует `Vec` в VFS и копирует его в буфер ответа. Декодирование WRITE (`Unpack` из `impl Read`) копирует payload в новый `Vec`. Плюс отдельный `tokio::spawn` на каждое сообщение и неограниченный канал ответов без backpressure. Здесь у nfs-mamont с аллокатором буферов за трейтом есть архитектурное преимущество (по описанию nfs-mamont; бенчмарками не проверено).
- Семантика безопасности слабая: права на уровне пользователя в VFS проверить нельзя (credentials не передаются), ACCESS «эхом» разрешает всё запрошенное, хук `authorize` — только allow/deny на вызов. Фактически контроль доступа остаётся на клиентском ядре по mode-битам из GETATTR.
- DRC «молча отбрасывать повтор» опасен там, где ответ потерян: при реконнекте с тем же `ip:port` клиент может не получать ответ до 60 с. Это вывод из кода, на практике не проверялся.
- `PROC_UNAVAIL` для LINK/MKNOD/DUMP вместо `NFS3ERR_NOTSUPP` (для NFS-процедур) — отступление от ожиданий RFC 1813 к поведению сервера. Клиенты могут обрабатывать это хуже, чем «not supported» (например, `ln` покажет ошибку I/O, а не EOPNOTSUPP). Это вывод, не проверенный тестом с ядром.

### Gaps
- Публичных бенчмарков throughput и latency нет. Есть bench-крейт (#149) и открытый issue #135 «cargo-nfs3-server: low write performance», но цифр я не нашёл.
- Поведение реальных клиентов (Linux, macOS, Windows) на `PROC_UNAVAIL` для LINK/MKNOD и на «молчаливый» DRC не проверялось.

## 5. Клиент nfs3_client и выигрыш для тестирования от «сервера и клиента в одном репозитории»

### Takeaway
nfs3_client — асинхронный клиент, не привязанный к runtime (свои IO-трейты, features `tokio` и `smol`). Он покрывает все 22 процедуры NFSv3, а также MOUNT и portmapper, и сам по себе популярен (около 23 тыс. загрузок). Главная польза для проекта — 88 интеграционных тестов «свой клиент ↔ свой сервер» в памяти процесса плюс E2E-прогон реального бинаря cargo-nfs3-server на 4 ОС в CI. Ограничения клиента: один запрос в полёте на клиента, IPv4/IP-only в коннекторе, перебор привилегированных портов.

### Inferences
- Связка «свой клиент + свой сервер» даёт дешёвые, детерминированные и кросс-платформенные E2E-тесты без root и монтирования, включая негативные RPC-кейсы и конкурентность. Это реальное преимущество в скорости разработки, и nfs-mamont может его повторить.
- Слабое место той же связки: обе стороны используют одни и те же `nfs3_types`, поэтому симметричная ошибка XDR-кодека (одинаково неверные кодирование и декодирование) тестами не ловится. Совместимость с ядрами Linux, macOS и Windows в CI не проверяется, conformance-наборов (pynfs и т. п.) в репозитории нет.
- Клиент — самостоятельный продукт (rattler, netget, links-fs, автор NFSWolf). Это канал adoption, которого у nfs-mamont нет как отдельного публичного крейта.

### Gaps
- Тесты не запускались: время прогона и стабильность (flaky) не известны, бейджей и статистики CI я не видел.

## 8. Итог: в чём nfs3 лучше nfs-mamont и в чём хуже

### Takeaway
nfs3 выигрывает adoption (около 44 тыс. против около 80 загрузок, ArcBox, conda/rattler, Lockbook), кросс-платформенностью сервера (Windows, macOS, Linux ARM в CI), экосистемой (публичный клиент на tokio/smol, CLI, memfs, RO-адаптер), простотой API и зрелой автоматизацией релизов. Проигрывает полнотой протокола (нет LINK, MKNOD, MOUNT DUMP, настоящего portmap/rpcbind, UDP), путём данных (нет zero-copy, аллокация и копия на каждый READ/WRITE), семантикой безопасности (нет credentials в VFS, ACCESS «эхом»), DRC без повтора ответа, отсутствием фаззинга и аудита, более высоким MSRV (1.88 против 1.75) и bus factor 1 при падающем каденсе. Для nfs-mamont это главный «наследник nfsserve» в нише библиотек, но не единственный: сам nfsserve с 2026-04 снова развивается в Hugging Face.

### Inferences
- В чём nfs3 лучше nfs-mamont:
  1. Реальное внедрение и доверие: около 44 тыс. против около 80 загрузок, ArcBox (4,3k★), conda/rattler, Lockbook.
  2. Кросс-платформенный сервер (Windows, macOS, Linux ARM) и документированные команды mount для трёх ОС-клиентов.
  3. Публичный runtime-agnostic клиент и E2E-тесты «свой клиент ↔ свой сервер» на 4 ОС.
  4. Готовый CLI и memfs для быстрого старта.
  5. Более простой и эргономичный trait API (RO/RW, методы по умолчанию, RO-адаптер, generic handle до 56 байт, общий generation number для кластера, хук `authorize`).
  6. Зрелая автоматизация релизов (release-plz, CHANGELOG, Conventional Commits) и быстрый merge внешних PR.
  7. Происхождение от nfsserve с кодом, обкатанным с 2023 года.
- В чём nfs3 хуже nfs-mamont:
  1. Неполный NFSv3: LINK, MKNOD и MOUNT DUMP недоступны, COMMIT появился только в 2026-04, в memfs нет symlink.
  2. Поддельный portmap без регистрации в rpcbind и без UDP.
  3. Нет zero-copy: аллокация и копирование на каждом READ/WRITE, `tokio::spawn` на каждое сообщение, неограниченная очередь ответов, ответы одним фрагментом.
  4. Слабая модель авторизации: нет per-call credentials в VFS, ACCESS не проверяет права.
  5. DRC отбрасывает повторы вместо повтора закэшированного ответа.
  6. Нет фаззинга, cargo-audit и udeps. Тесты в основном через собственный клиент с общими `nfs3_types`, поэтому симметричные ошибки кодека не видны, тестов с ядерными клиентами нет.
  7. Выше MSRV (1.88 против 1.75).
  8. Bus factor 1, падающий каденс, около 10 breaking-релизов, частично устаревшие README.
  9. Нет заявленного roadmap к NFSv4 и NLM/NSM.
- Что nfs-mamont стоит позаимствовать:
  - отдельный публичный клиент или хотя бы тестовый клиент в workspace для E2E-тестов без root;
  - кросс-платформенную матрицу CI (хотя бы macOS как сервер, если это цель);
  - RO-адаптер и `bind_ro`, кластерный generation number, хук авторизации;
  - CLI `cargo install …` как витрину;
  - release-plz и CHANGELOG.
- Где дифференцироваться и как позиционироваться:
  - «полный RFC 1813, включая LINK, MKNOD и DUMP» — подтверждать тестами с ядерными клиентами Linux (а у nfs3 их нет);
  - zero-copy с цифрами бенчмарков против nfs3_server и nfsserve;
  - корректный DRC и per-call credentials;
  - rpcbind;
  - fuzzing;
  - путь к NLM/NSM и NFSv4.
- Конкурентная угроза: nfs3 уже закрепился в инфраструктурных продуктах (ArcBox, conda/rattler) благодаря кросс-платформенности, а это именно та ниша user-space NFS для macOS и Windows без FUSE, куда Linux-only nfs-mamont сейчас не попадает.

### Gaps
- Сравнительных бенчмарков nfs3_server против nfs-mamont нет, по производительности без измерений выводы делать нельзя.
- Заявление nfs-mamont о «full procedure set of RFC 1813», его DRC и модель передачи credentials в `Vfs` в этой работе не проверялись. Подтверждены только наличие под-трейтов `Link` и `MkNode`, клиента rpcbind и CI-джобов.
- Совместимость с реальными ядерными клиентами (Linux, macOS, Windows) не проверена ни для одного из двух проектов.
