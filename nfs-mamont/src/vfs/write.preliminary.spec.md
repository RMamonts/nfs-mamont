## 2. Mechanics

Here you need to list the key mechanisms implemented in this module. 
A key mechanism can be identified by its semantic complexity and/or its public visibility.

Intent:
- To define the interface and data structures for the NFSv3 `WRITE` procedure.
- To encapsulate the requirements for data durability (`StableHow`) and cache consistency (`Verifier`, `WccData`) associated with writing data to a file.
- To separate the parsing of the data payload from the metadata arguments via `ArgsPartial`.

Inputs:
- **`Args<B>`**: A structure containing the file handle, offset, size, stability requirement, and the data buffer itself.
- **`ArgsPartial`**: A structure containing the metadata fields of `Args` (file, offset, size, stable) but excluding the data buffer. This facilitates staged parsing where the buffer might be processed separately.

Outputs:
- **`Result<Success, Fail>`**: The result of the write operation.
  - **`Success`**: Contains the number of bytes written, the actual stability level achieved, a verifier for unstable writes, and Weak Cache Consistency (WCC) data.
  - **`Fail`**: Contains the VFS error and WCC data.

Steps:
1. **Interface Definition**: The module defines the `Write<B: Buffer>` trait, marked with `#[trait_variant::make(Send)]`. This macro transforms the async trait definition into an object-safe trait that is also `Send`, allowing it to be used in dynamic dispatch scenarios across threads.
2. **Argument Handling**: The `Args` struct aggregates the parameters required for the write. The `ArgsPartial` struct allows the RPC layer to decode the fixed-size arguments before potentially handling the variable-length data buffer.
3. **Stability Negotiation**: The `StableHow` enum defines the contract for data persistence:
   - `Unstable`: The server may acknowledge before data is on stable storage.
   - `DataSync`: Data must be on stable storage; metadata is optional.
   - `FileSync`: Both data and metadata must be on stable storage.
4. **Result Construction**: The `Success` struct includes a `Verifier`. This is a cookie generated by the server that the client must store and later send back in a `COMMIT` operation to verify that unstable data has been committed to stable storage.
5. **Error Handling**: The `Fail` struct wraps a `vfs::Error`. The trait documentation specifies that implementations may return `vfs::Error::NoSpace` instead of `vfs::Error::QuotaExceeded` in certain conditions, and must return `vfs::Error::InvalidArgument` if the target file is not a regular file.

Edge Cases:
- **Short Writes**: The documentation for `Args` notes that if the data size exceeds the server's `write_max`, the server may perform a short write (writing fewer bytes than requested).
- **Quota vs. NoSpace**: Implementations have discretion to map quota failures to `NoSpace` errors.

Complexity:
- Time: O(1) for struct construction and enum definition. The complexity of the actual `write` operation depends on the implementation of the trait.
- Space: O(1) for metadata structures. O(N) for the data buffer `B`, where N is the size of the data being written.

Determinism:
- Deterministic (Interface definition).

## 4. Data Model

Entities:
- **`StableHow`**: An enum representing the level of data durability required by the client (`Unstable`, `DataSync`, `FileSync`).
- **`Verifier`**: A newtype wrapper around a fixed-size byte array `[u8; NFS3_WRITEVERFSIZE]`. It acts as a cookie to detect server reboots between unstable writes and commits.
- **`Args<B: Buffer>`**: The complete argument set for a write request, including the file handle, offset, size, stability requirement, and the data buffer.
- **`ArgsPartial`**: The argument set excluding the data buffer, used for parsing.
- **`Success`**: The successful result of a write operation, containing `file_wcc` (cache data), `count` (bytes written), `committed` (actual stability), and `verifier`.
- **`Fail`**: The failed result of a write operation, containing `error` and `wcc_data`.

Relations:
- **Composition**: `Args` contains a `file::Handle` and a generic `B` implementing `Buffer`.
- **Association**: `Success` and `Fail` both contain `vfs::WccData`.
- **Dependency**: `Verifier` size depends on `NFS3_WRITEVERFSIZE`.

Global Invariants:
- **Verifier Size**: The `Verifier` struct always contains exactly `NFS3_WRITEVERFSIZE` bytes.
- **File Type**: The `file` field in `Args` must refer to a `Type::Regular` file for the operation to succeed; otherwise, `vfs::Error::InvalidArgument` is returned.

## 5. Error Model

Error Types:
- `vfs::Error` (wrapped in `Fail`)

Error Propagation Strategy:
- The `write` method returns a `Result<Success, Fail>`. Errors are wrapped in the `Fail` struct, which includes the specific `vfs::Error` and `wcc_data` to allow the client to update its cache even on failure.

Recoverability:
- Recoverable. The client receives the error and can retry or abort the operation based on the error code.

Panics:
- Allowed: No (in the interface definition).
- Conditions: The interface itself does not panic. Implementations may panic, but the trait definition does not specify panic conditions.

This module is used in order to define the contract for modifying file content within the NFSv3 server implementation. The system contains a complex Virtual File System (VFS) layer that translates network requests into storage operations. A typical usage scenario of the system involves a client sending a WRITE request over the network. The RPC layer decodes the request into `Args` (potentially using `ArgsPartial` to handle the header before the data payload arrives). The system then invokes the `Write` trait implementation provided by the specific storage backend (e.g., local disk, in-memory, or cloud storage).

Inside the system, the following things happen and they use this module: The storage backend receives the `Args`, which include a `Buffer` containing the data to be written. The backend writes this data to the specified `offset` of the file identified by the `Handle`. The `StableHow` parameter dictates the synchronization cost of the operation; `FileSync` requires a full `fsync`, while `Unstable` allows the server to acknowledge immediately for performance. If `Unstable` is used, the backend generates a `Verifier` and returns it in `Success`. The client must later send this `Verifier` in a `COMMIT` request to ensure data durability. The `WccData` returned in both `Success` and `Fail` allows the client to update its attribute cache efficiently. Without this module, the VFS layer would lack a standardized way to handle the specific semantics of NFSv3 writes, such as weak cache consistency and unstable write verification, leading to potential data corruption or cache coherency issues in a distributed environment.
