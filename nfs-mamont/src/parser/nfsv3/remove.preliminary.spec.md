## 2. Mechanics

Here you need to list the key mechanisms implemented in this module. 
A key mechanism can be identified by its semantic complexity and/or its public visibility.

Intent:
- To deserialize the raw byte stream of an NFSv3 `REMOVE` procedure call into a structured `remove::Args` object suitable for consumption by the VFS layer.

Inputs:
- `src: &mut impl Read`: A mutable reference to a byte stream containing the serialized arguments for the NFSv3 `REMOVE` operation.

Outputs:
- `Result<remove::Args>`: A result containing the parsed arguments or a `parser::Error` if the stream is malformed or contains invalid data.

Steps:
1. **Directory Handle Parsing**: The function calls `file::handle(src)` to read and validate the file handle of the directory containing the target entry. This advances the stream cursor.
2. **Filename Parsing**: The function calls `file_name(src)` to read and validate the variable-length string representing the name of the entry to be removed.
3. **Structure Construction**: The parsed handle and name are combined into a `vfs::DirOpArgs` structure.
4. **Result Packaging**: The `vfs::DirOpArgs` is wrapped inside `remove::Args` and returned.

Edge Cases:
- **Malformed Handle**: If the file handle in the stream does not meet the protocol requirements (e.g., incorrect length), `file::handle` will return an error, which propagates immediately.
- **Invalid Filename**: If the filename is too long, contains null bytes, or violates other constraints, `file_name` will return an error.
- **Short Stream**: If the stream ends unexpectedly before the handle or name is fully read, an `IO` error will be returned.

Complexity:
- Time: O(N), where N is the size of the file handle plus the length of the filename string.
- Space: O(N), primarily for the allocation of the filename string and the resulting structures.

Determinism:
- Deterministic. Given the same input byte sequence, the function will always produce the same `remove::Args` structure or the same error.

This module is used in order to bridge the gap between the raw network protocol format of the NFSv3 `REMOVE` operation and the high-level Virtual File System (VFS) abstraction used by the server. The system receives binary streams over the network representing client requests. Without this module, the server would lack the specific logic to interpret the byte sequence unique to the `REMOVE` procedure (a directory handle followed by a filename) and convert it into the `remove::Args` structure required by the VFS to execute the deletion.

This system contains a hierarchy of parsers where generic file parsing primitives (handles, strings) are composed into specific operation parsers. The `parser::nfsv3::remove` module is a specific composer that orchestrates these primitives to match the NFSv3 specification for the `REMOVE` procedure.

A typical usage scenario of the system involves an RPC dispatcher receiving a `REMOVE` request. The dispatcher extracts the argument bytes and passes them to this module's `args` function. The function validates the structure and content of the bytes (ensuring the handle is the correct size and the name is valid) and returns a `remove::Args` object. This object is then passed to the VFS `Remove` trait implementation, which performs the actual file system unlink operation.

Inside the system the following things happen and they use this module:
- **Protocol Decoding**: The system relies on this module to enforce the wire format order (handle then name) defined by the NFSv3 RFC.
- **Validation**: By delegating to `file::handle` and `file_name`, the module ensures that malformed data (e.g., oversized filenames) is rejected before it reaches the VFS layer, protecting the storage backend from invalid inputs.
