## 2. Mechanics

Here you need to list the key mechanisms implemented in this module. 
A key mechanism can be identified by its semantic complexity and/or its public visibility.

Intent:
- To implement the `FsInfo` trait for the `MirrorFS` struct, enabling the NFS server to report the capabilities, limits, and attributes of the mirrored file system to clients.
- To translate an abstract file handle (provided in the arguments) into concrete file system attributes and static configuration parameters.

Inputs:
- **`args: fs_info::Args`**: Contains a `root` file handle identifying the file system instance or mount point being queried.

Outputs:
- **`Result<fs_info::Success, fs_info::Fail>`**:
 - **`Success`**: Contains the root attributes, I/O size limits (read/write), directory reading preferences, maximum file size, time granularity, and supported properties (flags).
 - **`Fail`**: Contains a `vfs::Error` if the handle resolution fails.

Steps:
1. **Handle Resolution**: The method calls `self.path_for_handle(&args.root).await` to convert the opaque NFS file handle into a local file system path.
2. **Error Handling**: If the handle resolution returns an `Err`, the method immediately returns `fs_info::Fail` containing that error and sets `root_attr` to `None`.
3. **Attribute Retrieval**: If the handle is valid, the method calls `Self::file_attr(&path)` to retrieve the metadata (attributes) for the root directory.
4. **Response Construction**: The method constructs a `fs_info::Success` struct with the following values:
 - **I/O Limits**: `read_max`, `read_pref`, `write_max`, and `write_pref` are set to the constant `READ_WRITE_MAX`. `read_mult` and `write_mult` are set to `1`.
 - **Directory Limits**: `read_dir_pref` is set to the constant `READ_DIR_PREF`.
 - **File Size**: `max_file_size` is set to `u64::MAX`.
 - **Time Granularity**: `time_delta` is set to `file::Time { seconds: 0, nanos: 1 }`, indicating nanosecond precision.
 - **Properties**: The properties bitmask is constructed using `fs_info::Properties::from_wire` with the flags `LINK`, `SYMLINK`, `HOMOGENEOUS`, and `CANSETTIME` enabled.

Edge Cases:
- **Invalid Handle**: If `args.root` does not correspond to a valid path known to `MirrorFS`, the operation fails and returns the error generated by `path_for_handle`.

Complexity:
- **Time**: Depends on the complexity of `path_for_handle` (likely a lookup in a map) and `file_attr` (likely a file system stat call). Typically O(1) or O(log N) for the lookup, plus the cost of a stat syscall.
- **Space**: O(1) for the returned structures.

Determinism:
- **Deterministic**: Given a valid handle, the returned constants and attributes are deterministic. The behavior on error depends on the specific error returned by the internal methods.

## 7. Overview

This module is used in order to **expose the specific capabilities and configuration limits of the `MirrorFS` backend to NFS clients**. The system contains a complex architecture where the storage backend (`MirrorFS`) must conform to the generic `Vfs` interface defined by the `nfs_mamont` library. This module is necessary because it provides the concrete logic that answers the "FSINFO" RPC call for this specific backend, translating generic protocol requirements into the specific behavior of the mirrored file system.

A typical usage scenario of the system involves a client mounting the `MirrorFS` export and issuing an `FSINFO` request to determine how to optimize data transfer. The RPC layer receives the request and calls the `fs_info` method implemented in this module. The module resolves the file handle to the local path, retrieves the root directory's attributes, and returns a `Success` struct. This struct tells the client, for example, that it supports symlinks (`SYMLINK` flag), that it can handle files up to `u64::MAX` in size, and that the preferred read/write size is `READ_WRITE_MAX`. The client then uses this information to size its I/O buffers correctly and avoid requesting unsupported operations.

Inside the system, the following things happen and they use this module:
1. **Capability Advertisement**: The module explicitly sets the `LINK`, `SYMLINK`, `HOMOGENEOUS`, and `CANSETTIME` flags. This tells the client that the underlying file system supports hard links, symbolic links, has consistent properties across the hierarchy, and allows setting file times.
2. **Performance Tuning**: By returning `READ_WRITE_MAX` for `read_pref` and `write_pref`, the module advises the client on the optimal block size for I/O operations, which is crucial for achieving high throughput over the network.
3. **Handle Validation**: The call to `path_for_handle` acts as a validation step. If the handle provided by the client is invalid or stale, the module returns an error, ensuring that attributes are only reported for valid, accessible file system roots.

Without this module, the `MirrorFS` struct would not satisfy the `Vfs` super-trait (which requires `FsInfo`), and the server would be unable to handle `FSINFO` requests, leading to protocol violations or client connection failures. This module effectively "wires" the static configuration of `MirrorFS` into the dynamic NFS protocol negotiation.

**Uncertainty**: The methods `path_for_handle` and `file_attr` are invoked on `self` and `Self` respectively but are not listed in the public interface facts for `MirrorFS`. It is assumed they are internal helper methods or part of a private interface within the `mirrorfs::fs` module.
